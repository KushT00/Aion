AION: An LLM-Orchestrated Workflow Automation Marketplace Sanket Saraf, Kush Tejani, Ricky Parmar Department of Artificial Intelligence & Data Science, K. J. Somaiya Institute of Technology, Sion, Mumbai, India Under the guidance of Prof. Pravin Patil Abstract: Building and deploying workflow automations remains difficult for non-technical users, and developers who build automations for clients have no easy way to package and resell that work. This paper presents AION, a full-stack marketplace platform that lets creators build workflow-based “digital workers” using a visual, node-based builder, and supports marketplace discovery and consumer workflow instances through a guided onboarding flow; payment and payout functionality is not implemented; billing  and earnings screens currently display placeholder (dummy) values for demonstration purposes. AION's core engineering contributions are a directed-acyclic-graph (DAG) execution engine with variable resolution and retry handling, a multi-tenant data model with row-level security, and an integration layer connecting workflow nodes to hosted large language models (Gemini,  Groq , and other configured providers) and third-party services through a registry-based integration layer. Unlike systems that rely on custo m fine-tuned classifiers for intent understanding, AION's conversational onboarding assistant is built directly on prompted calls to hosted LLM APIs — a deliberate engineering trade-off discussed in Section 6. This paper reports the system's actual implementation status as of submission: core execution infrastructure is complete and has been exercised through informal development-time testing; the platform's central value proposition for non-technical creators — automatic workflow generation from natural la nguage — is designed but not yet implemented. No formal accuracy, precision, or user-study benchmarks are claimed; all reported figures are explicitly  labeled  as informal internal observations, and the paper's contribution is presented as a system architecture and an honestly-scoped implementation status, together with a concrete roadmap for the evaluation work that remains. Keywords: Workflow Automation, LLM Integration, Visual Workflow Builder, DAG Execution Engine, Marketplace Architecture, API Integration, Conversational Onboarding. 1. INTRODUCTION Workflow automation has become a valuable capability in modern digital work, yet the tools available today still demand technical knowledge most users do not have. Platforms such as Zapier, Make, and n8n have lowered the barrier somewhat, but configuring multi-step workflows with API authentication and conditional logic remains genuinely difficult for non-programmers. Separately, developers who build automation solutions for clients repeatedly recreate similar workflows from scratch, with no straightforward  way to package that work into a  resellable  product. AION addresses both sides of this problem through a marketplace architecture: creators build workflows using a visual, node-based editor and publish them for sale; consumers browse the marketplace, obtain workflow instances, and are guided through connecting their own credentials (API keys, account access) via a conversational onboarding assistant; payment and payout support is not implemented; billing and earnings screens currently use placeholder values for demonstration. This paper documents AION as it c urrently exists: a working platform with a complete execution engine, database layer, and builder interface, integrated with hosted large language model APIs for its conversational and AI-assisted features. This paper makes a deliberate choice that distinguishes it from a typical applied-ML paper: it does not claim to have trained or evaluated custom machine-learning models, because none were trained for this system. AION's “AI” capability comes from orchestrating calls to general-purpose hosted LLMs (Google Gemini,  Groq -hosted Llama models) rather than from fine-tuned intent classifiers, sequence taggers, or ensemble classifiers. Section 2 reviews related work in conversational AI, no-code automation, and agent architectures. Section 3 describes AION's system architecture. Section 4 covers implementation details. Section 5 reports the system's actual development status, informal testing observations, and a concrete roadmap of unresolved evaluation work. Section 6 discusses limitations in depth, Section 7 covers ethics  and broader impact, and Section 8 concludes. 2. LITERATURE SURVEY The following sections review work published between 2018 and 2026 across three areas directly relevant to AION's actual architecture: conversational AI, no-code workflow automation, and LLM-based agent frameworks. Unlike an earlier draft of this work, this survey does not include semantic-retrieval or fraud-detection literature, since AION does not implement a trained semantic matcher or a trained fraud classifier; the marketplace currently relies on standard keyword search and filtering, and no fraud-dete ction component has been built. 2.1 Conversational AI and LLM-Based Assistants Coucke et al. [1] presented Snips NLU, a task-oriented dialogue pipeline using CRF-based slot filling, demonstrating that structured, trained NLU pipelines can achieve strong intent accuracy within narrow domains. Mehri et al. [2] introduced  DialoGLUE , a benchmark and pre-trained model suite for dialogue understanding across eight datasets. Both works represent the classical, trained-classifier approach to conversational interfaces. AION's onboarding assistant instead follows a more recent and increasingly common alternative: it is built directly on a general-purpose hosted large language model (LLM), prompted with a task-specific system instruction, rather than a custom fine-tuned classifier. This trades the measurable benchmarks that trained  models provide for faster iteration, broader language coverage, and no training-data collection burden — a trade-off made explicit and evaluated honestly in Section 6 of this paper. 2.2 Workflow Automation and No-Code Platforms Martínez- Lasaca  et al. [3] examined low-code and model-driven engineering approaches for domain-specific automation platforms, noting that most existing tools still require some level of technical specification from the user.  Ristov  et al. [4] studied LLM-based serverless workflow generation, evaluating how well language models can synthesize executable workflow definitions from natural-language descriptions — a capability directly relevant to AION's planned AI Agent Creation Wizard (Section 6). Zhao et al. [5] prop osed self-adaptive abstraction operators for agentic workflow generation, offering a mechanism for automatically composing lower-level actions into higher-level, reusable workflow steps. These works collectively motivate AION's architectural choice to separate a general-purpose visual workflow builder (for technical creators, implemented today) from an automated natural-language-to-workflow generation capability (for non-technical creators, planned but not yet implemented). 2.3 AI Agent Architectures and Tool Use Wu et al. [6] introduced  AutoGen , a framework for building LLM applications through multi-agent conversation, where specialized agents collaborate to complete complex tasks. Yao et al. [7] proposed  ReAct , which interleaves reasoning traces with actions, allowing an LLM to decide which tool to invoke based on intermediate reasoning steps. Schick et al. [8] presented  Toolformer , showing that language models can learn to invoke external APIs (calculators, search engines, translators) by self-supervised training on API-call examples. S hridhar et al. [9] introduced  ALFWorld , an interactive text-and-embodied environment used to evaluate language agents on multi-step tasks. Li et al. [10] introduced API-Bank, a benchmark for evaluating how well LLMs can select and call the correct API from a large tool library. Together, these works establish the pattern AION's execution engine follows at a systems level: a workflow node calls an external API (an LLM, or a third-party integration such as Discord or Slack) and the result is passed to the nex t node in the graph. Unlike  ReAct  or  Toolformer , AION does not use a trained or fine-tuned model to decide which tool to call — tool selection is explicit and deterministic, defined by the workflow graph the creator builds. 2.3.1 Directly Comparable No-Code Agent Platforms Tang et al. [11] presented  AutoAgent , a fully automated, zero-code framework in which natural-language instructions are converted directly into working LLM agents and workflows. Lande and  Strashnoy  [12] proposed AgentFlow, an orchestration and synchronization layer for coordinating no-code agents. Yasser et al.  [13] introduced  Autonoma , a hierarchical multi-agent framework for workflow automation using a coordinator/planner/supervisor pattern.  Palayamkot  and Karim [14] presented MASON, a multi-agent LLM framework aimed specifically a t no-code development. These four systems are the closest published comparators to AION's stated goal — a marketplace where non-technical users can obtain working automations through natural-language interaction.  AutoAgent , in particular, targets the exact automatic-generation capability that AION's roadmap identifies as its next major milestone (Section 6.2). SYSTEM ARCHITECTURE AION is organized as four principal layers: a Next.js frontend, a  Supabase -based backend and data layer, a server-side TypeScript DAG execution engine, and an integration layer that connects workflow nodes to external APIs. Figure 1 shows this architecture as actually implemented in the codebase, including which connections are live and which (dashed) are planned but not yet built. Figure 1. AION System Architecture, as implemented (Source: Authors' own design, derived from the project codebase) 3.1 Frontend The frontend is built with Next.js 16 (App Router), TypeScript, and Tailwind CSS. The workflow builder uses React Flow to provide a drag-and-drop canvas backed by 33  catalog  entries spanning 13 node-type families in the supplied implementation. The interface includes a marketplace browser with category-based search and filtering, a creator dashboard for managing published workflows, and a consumer dashboard showing active automations and run history. 3.2 Backend and Data Layer AION uses  Supabase  for authentication (email/password and Google OAuth), a PostgreSQL database with row-level security (RLS) policies for tenant-scoped data access, and object storage for uploaded assets. The data model includes tables for marketplace listings, purchases, ratings, encrypted user credentials (a per-user credential vault), wallets and transactions, consumer workflow instances, run logs, and workflow analytics. 3.3 Execution Engine Workflows are represented as a JSON directed acyclic graph, with each node specifying a type (trigger, AI action, integration action, condition, or output), configuration parameters, and edges defining execution order. The execution engine, implemented in server-side TypeScript, performs a topological traversal of the graph. A variable resolver substitutes template expressions (for example, referencing a prior node's output) before each node executes. A configurable retry handler tracks attempts and waits f or a fixed delay between retry attempts. Execution status and per-node output are emitted through the runner's log/callback interface, while completed run logs are persisted for later inspection. 3.4 Integration and AI Layer Workflow nodes that require external capability call hosted APIs directly, rather than any model trained as part of this project. AI-capable nodes and the conversational onboarding assistant call hosted large language models, including Google Gemini and  Groq -hosted Llama models, with task-specific prompts; the registry also contains support for other configured providers such as OpenAI and  OpenRouter . Third-party service integrations are exposed through a common integration-registry pattern; the supplied implementation contains registered modules for services including Discord, Telegram, Slack, Notion, Google Workspace, webhooks, forms, and utility actions, with production readiness varying by connector. No real payment gateway is integrated, and the billi ng and creator-earnings interfaces use placeholder/demo values rather than a live payment transaction system. 3.5 Marketplace Purchase and Instance Provisioning When a consumer purchases a listing through the primary marketplace purchase endpoint, the platform performs a deep clone of the creator's workflow rather than granting shared access to the original: a new workflow record is created under the buyer's account, nodes and edges are copied with freshly generated identifiers, and internal tool/knowledge- base  references in node configurations are remapped to the cloned identifiers so the buyer's copy is independently editable. A corresponding row is created in  consumer_instances , linking the purchase record to the cloned workflow with an initial status of  setup_required . The purchase record itself (buyer, listing, price, pricing tier) is written to the purchases table, while duplicate purchases and self-purchases are rejected. The endpoint records the purchase and provisions the instance, but it does not ch arge a real payment instrument; this is consistent with the placeholder billing described in Section 3.4. Once the buyer has supplied the required credentials (Section 3.6), the instance can be toggled active and is picked up by the execution engine on subsequent runs. 3.6 Conversational Onboarding Assistant When a consumer purchases a workflow, AION guides them through connecting the credentials that workflow requires (for example, an API key for a service the workflow calls) using a chat interface. This assistant is implemented as a system-prompted call to a hosted LLM: the model is given the purchased workflow's required credential schema and instructed to ask the user for each missing value conversationally, validate that a provided value looks well-formed, and confirm completion. This is deliberately diffe rent from the trained intent-classification-and-slot-filling architecture (CRF over a fine-tuned encoder) described in the agent-architecture literature reviewed in Section 2.1 [1], [2]: AION uses no training data of its own for this component, and its  behavior  is entirely determined by the prompt given to the underlying hosted model. 4. IMPLEMENTATION DETAILS 4.1 Technology Stack Frontend: Next.js 16, React, TypeScript, Tailwind CSS, React Flow,  Zustand  for client state, and  TanStack  Query for server-state caching. Backend and data:  Supabase  (PostgreSQL, Auth, Realtime, Storage). Server-side execution: TypeScript workflow runner and integration registry. AI and integrations: direct API calls to Google Gemini and  Groq , plus third-party connector modules including Discord and other registered services.  No machine-learning training framework ( PyTorch , TensorFlow, scikit-learn) is used anywhere in the supplied code sample, because no models are trained  as part of this system. 4.2 Data Model The PostgreSQL schema includes tables for  marketplace_listings , purchases, ratings, a per-user encrypted credential vault, wallets and transactions,  consumer_instances  (a consumer's running copy of a purchased workflow),  consumer_credentials ,  consumer_run_logs ,  consumer_analytics , notifications, and conversations/messages for the onboarding chat. Row-level security policies scope user-facing database access to the authenticated user's own data; selected server-side routes use a  Supabase  service-role client for privileged cloning and execution opera tions. 4.3 Integration Registry Pattern Each supported third-party service is implemented as an integration module exposing a stable identifier, a display name, and a list of callable actions, each with its own execution function and expected input schema. This pattern allows new integrations to be added without modifying the core DAG execution engine, and is the mechanism by which additional connectors (Slack, Telegram, Notion, Google Workspace) are currently being added. 5. LIMITATIONS AND FUTURE WORK AION's capabilities are currently bounded by the hosted LLM providers it calls; response quality, latency, and cost are outside the authors' control and are not benchmarked in this paper. The system's central non-technical-user value proposition — automatic workflow generation from natural language — is designed but not implemented; until it exists, AION functions primarily as a marketplace and execution platform for manually-built workflows, and comparisons with fully automated systems such as  AutoAgent  [11] or  Autonoma  [13] should be read as aspirational rather than empirical. Payment and payout functionality is incomplete, so no real creator-earnings data exists. No formal usability study with non-technical participants has been conducted, no load or scalability testing has been performed beyond the informal observations in Table 4, and total real-world usage to date is very small (on the order of tens of workflow runs). Future work is organized around closing these specific gaps: (1) implement and evaluate the AI Agent Creation Wizard, including a real comparison against  AutoAgent , AgentFlow,  Autonoma , and MASON on a shared task set; (2) integrate a real payment gateway (e.g., Stripe) to replace the current placeholder billing and earnings interface, and measure real creator earnings; (3) conduct a System Usability Scale (SUS) study with 10–15 genuinely non-technical participants completing defined tasks; (4) run controlled load tests (10, 50, 100, and 500 concurrent executions) using Locust or k6 and report p50/p95 latency and error rate; (5) evaluate, as a research questi on rather than an assumption, whether a purpose-built model would outperform general LLM prompting for specific sub-tasks such as marketplace search ranking or credential-format validation; and (6) publish the source code publicly, subject to review of any third-party licensing constraints. 7. ETHICS, PRIVACY, AND BROADER IMPACT AION stores user credentials (API keys and account tokens needed to run purchased workflows) in an encrypted per-user vault, and row-level security policies scope all database access to the authenticated user. Because the onboarding assistant and AI-capable workflow nodes call third-party hosted LLM APIs (Gemini,  Groq ), user-provided text and, potentially, workflow context data are transmitted to those providers subject to their own data-handling terms; this paper does not claim any formal data-protection certification (GDPR, CCPA, or India's DPDP Act) and treats third-party API data flow as a disclosure obligation to end users rather than a solved problem. As the marketplace grows, ranking and moderation mechanisms will need explicit fairness and abuse-prevention consideration — currently, discovery is a simple cat egory-based search with no ranking algorithm to audit. The environmental and cost footprint of routing workflow execution through hosted LLM calls is acknowledged as a real, if currently unmeasured, cost of the architecture's design. 8. CONCLUSION AION is a working, early-stage marketplace platform for workflow automation, built on Next.js and  Supabase , with a complete DAG-based execution engine, a multi-tenant data model, and a conversational credential-onboarding assistant built on hosted LLM APIs. Its core engineering contribution is the execution architecture and integration pattern documented in Sections 3 and 4, not a trained machine-learning system. This paper deliberately reports the platform's actual, current implementation status rather than a set of benchmark results, because the machine-learning components originally planned for the s ystem — a fine-tuned intent classifier, a semantic marketplace matcher, and a fraud-detection ensemble — were not built. The most consequential remaining gap is the AI Agent Creation Wizard, the feature that would let non-technical users generate a working automation from natural language alone; without it, AION today serves technical creators better than the non-technical end users it ultimately targets. The roadmap in Section 6 identifies the specific, concrete evaluation work — a real comparison against  AutoAgent , AgentFlow,  Autonoma , and MASON, a genuine  usability study, and formal load testing — required before AION's accessibility and scalability claims can be made with empirical support.
